Kolaboro / Docs / Partners

Risk feed for banks and insurers

The same anonymous open data as our open API, shaped for underwriting and lending checks: one record of risk fields per project id, a change stream with a cursor, every answer signed with Ed25519. No developer names, no project names, no addresses: projects are ids like BALI-024, as in the open data.

Calling the sandbox and checking the signature in your browser…

1. Get access

  1. Sandbox, now: send x-api-key: kb_sandbox_public. It is public on purpose: real data, pages of at most 10, 120 calls per hour per IP address. Use it to build and test your integration.
  2. Free key: create a kb_live_... key on the API key page. It is shown once and only its SHA-256 is stored. Pages up to 500, 60 calls per minute per key, and a daily quota shared with the metered open API (1,000 calls a day on the free plan, as listed on that page).
  3. Higher limits: by agreement, write to hello@kolaboro.com. There is no paid tier yet, so there is no price to show.

2. Endpoints

RequestWhat it returns
GET /api/x/z/feed/projectsRisk fields per project, sorted by id. Parameters: limit (1 to 500, sandbox 10, default 100), cursor (from next_cursor), ids (comma separated, up to 100), market (market or country name).
GET /api/x/z/feed/changes?since=YYYY-MM-DDEvery recorded change to a project field on or after since, oldest first. Parameters: since, limit, cursor. Each change has a stable id for de-duplication.
GET /api/x/z/feed/schema.jsonJSON Schema (2020-12) of both answers. No key.
GET /api/x/z/feed/statusWhich sources are present, the data date, whether signing and live keys are on, and the limits. No key.

Pagination is by cursor: pass next_cursor back as cursor until it is null. Cursors name the last item you saw (an id, or a date, project and position), so they keep working when the data is updated between pages. Changes are recorded by the daily data run with a date and no time: to poll, keep the last cursor, or ask again with since set to the last date you saw and drop ids you already have.

3. Fields per project

FieldMeaning and source
disclosure_scoreHow many of six checks are public (permit number, deposit protection, construction progress, plans, track record, no guaranteed returns), 0 to 6. How we score.
disclosureEach check as published: true, false, null for not stated; progress is a percentage when the source gives one.
verification_levelPer check: registry (an official register confirms it), independent, developer (only the developer says so), contradicted, or none. confirmed_score counts registry and independent.
overdue_months, delay_monthsMonths past the promised handover, and announced delay, when public. null otherwise.
claims, public_problemsDeveloper claims tested (verified, unverified, contradicted) and public problems recorded.
satellite, registerLatest satellite change status and official register check, when there is one.
hazardsFrom /data/hazards.json: height, 100-year river and coastal flood depth, earthquakes M5+ within 100 km since 1900, tsunami run-ups within 50 km, nearest Holocene volcano, distance to the coast. Rounded so it cannot pinpoint a plot. null for projects without coordinates; 168 projects have them today. Sources and method.
on_timeFrom /data/on-time.json: the project's handover status, first and current handover month, months moved, and estimate: the share of closed comparable projects that handed over within 6 months of their first date, with a 95% interval and the number of comparables. Today there are few closed projects, so the estimate is pooled over all markets and is a floor, not a forecast; notes.on_time carries that file's own caveat. If the file is missing, the field is omitted.
page_fingerprint, last_checkedSHA-256 of the developer page we last read and the date; provable against the public log with /api/open/proof/{id}.

Every answer also carries dataset_sha256: the SHA-256 of the open dataset file it was computed from. That fingerprint is written to the public log each day and timestamped in Bitcoin, so a figure you relied on can be shown later to be what we published that day. Scores describe what is public, not whether a developer is honest, and they are not a valuation or a credit rating.

5. Verify every answer

Each answer has x-kolaboro-signature: base64 Ed25519 over "kolaboro-sig-v1\n" + SHA-256 hex of the exact body, and x-kolaboro-key-id. Public keys: /.well-known/kolaboro-keys.json. It is the scheme of the open API and of our signed webhooks. The body holds timestamp (Unix seconds) so a replayed old answer can be refused.

#!/bin/sh # Fetch one page of the feed and verify its Ed25519 signature with curl and OpenSSL 3. URL=${URL:-"https://kolaboro.com/api/x/z/feed/projects?limit=10"} KEY=${KOLABORO_KEY:-kb_sandbox_public} curl -s -D headers.txt -H "x-api-key: $KEY" "$URL" -o body.json grep -i '^x-kolaboro-signature:' headers.txt | cut -d' ' -f2 | tr -d '\r' | base64 -d > sig.bin # public key (SPKI) from https://kolaboro.com/.well-known/kolaboro-keys.json curl -s https://kolaboro.com/.well-known/kolaboro-keys.json | python3 -c "import json,sys; k=[x for x in json.load(sys.stdin)['keys'] if x['status']=='active'][0]; print('-----BEGIN PUBLIC KEY-----\n'+k['public_key_spki_b64']+'\n-----END PUBLIC KEY-----')" > kolaboro.pem # signed message = "kolaboro-sig-v1\n" + SHA-256 hex of the exact body printf 'kolaboro-sig-v1\n%s' "$(sha256sum body.json | cut -d' ' -f1)" > msg.txt openssl pkeyutl -verify -pubin -inkey kolaboro.pem -rawin -in msg.txt -sigfile sig.bin

6. Limits and errors

KeyPer minutePer hourPer dayPage
Sandbox kb_sandbox_public-120 per IP address-10
Free kb_live_...60 per key-daily quota of the key (free plan 1,000), shared with /api/x/k/m/*500

Headers x-ratelimit-limit and x-ratelimit-remaining (daily quota, or the sandbox hour), and x-ratelimit-burst-limit / x-ratelimit-burst-remaining for the minute. The per-minute counter is kept at each Cloudflare location, so it is approximate across locations; the daily quota is exact. Errors are JSON: 401 missing_key, 429 rate or quota, 400 bad_cursor or bad_since, 503 keys_unavailable (the sandbox keeps working).

7. Service level

There is no contractual SLA and no service credits. What we publish instead is measured, not promised: the service level objectives on /status, computed from outside probes when the page loads. The feed runs on the same worker and data as the API those probes check, but the probes do not call the feed itself.

Loading the current objectives…

The data is refreshed by a daily run; the freshness objective (90% of projects re-read from their source within 7 days) is reported at /api/open/freshness. If the hazards file is unavailable, hazards is null and notes.hazards says so; we never fill a gap with an estimate.

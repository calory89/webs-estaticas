Kolaboro / Verify evidence

Check that a photo or document from a Kolaboro report is genuine.

Your browser fingerprints the file locally. If it matches our public timestamp record, you get a proof anchored in Bitcoin that you can check independently.

Live · anchored in Bitcoin

Verify a piece of evidence yourself

Drop any photo or document from a Kolaboro report. Your browser computes its SHA-256 fingerprint; the file never leaves your device. We look the fingerprint up in our public timestamp record and give you the OpenTimestamps proof, which you can check with free, independent tools.

How it works: each fingerprint is submitted to independent OpenTimestamps calendars (run by the OpenTimestamps project and Eternity Wall). They aggregate it into a Bitcoin transaction within hours. After that, nobody, including us, can backdate or alter the evidence without it showing.

For clients and their lawyers

Check a case-file PDF

Every case-file PDF the portal creates is registered with its SHA-256 at the moment it is made. Choose the PDF: your browser computes its fingerprint (the file never leaves your device) and asks whether Kolaboro registered exactly these bytes. Any edit, even one character, gives a different fingerprint.

Check a whole case file

In the client portal, "Evidence data" downloads every fingerprint in a case. Drop that file here: your browser recomputes the chain item by item and tells you if anything was changed, removed or reordered.

Check that a project's record was sealed

Our research agent fingerprints every developer page it reads. All fingerprints go into one Merkle root that is written to the public log and timestamped in Bitcoin. Type a project ID: your browser fetches a short proof and recomputes the root itself.

Check that an answer really comes from Kolaboro

Every answer of our open data API and every evidence receipt is signed with our Ed25519 key. The public key is at /.well-known/kolaboro-keys.json. Your browser fetches the answer and checks the signature itself.

Any /api/open address, or an evidence number from a report (for example 27) to get its signed receipt.

Check a verifiable credential

Kolaboro issues sealed register lookups and delivered reports as W3C Verifiable Credentials. The issuer is did:web:kolaboro.com; its public key is in /.well-known/did.json (the same Ed25519 key as above). The proof uses the eddsa-jcs-2022 cryptosuite, so any standards-based verifier can check it. Paste a credential or open its file: your browser checks the signature itself and nothing is uploaded.

Where to get one: the "signed credential" link under a sealed lookup on /check, or "Download credential" next to a delivered report in your portal.

Check a dataset you downloaded

Drop a copy of bali-cases.json. Your browser computes its SHA-256 and looks for it in the public log. Every API answer also tells you which dataset it came from, in the x-kolaboro-dataset-sha256 header.

These checks run on kolaboro-verify.js, our open-source checker (MIT). You can run the same code on your own machine.

Check that a page is the page we published

After each deploy a GitHub Actions job takes the git commit the live site is serving and computes the SHA-256 of every published file outside /data/. The worker serves that list, signed with the same Ed25519 key as the open API, at /api/x/n/manifest. Your browser fetches a page again without cache, plus every script and stylesheet of our own that it loads, hashes each one and compares it with the signed list. Every page that shows the footer link "Verify this page" runs the same check on itself.

Exactly what is normalized before hashing the HTML

Our HTML files are changed on the way to you in three known ways, and each is reversed before hashing. Nothing else is touched; any other difference shows as a mismatch.

  1. The worker stamps a fresh nonce="..." on every <script> tag of each response (it is the key of our Content Security Policy, so it must change every time). The attribute is removed.
  2. Cloudflare hides email addresses from spam bots: a mailto: link becomes /cdn-cgi/l/email-protection#<hex>, the address becomes a [email protected] placeholder, and a script email-decode.min.js is added. The hex is decoded back to the address and the script removed.
  3. On two pages (/admin and one campaign landing) the worker appends a script from /__k/. It is removed.
  4. Only if the hash still does not match: the Google Analytics snippet just before </head> and the Microsoft Clarity snippet just before </body> are removed, because the deploy adds them to the few pages whose source has none. The result says when this step was needed.

Pages built per request (/p/<id> and /m/<market>) cannot match a static file, so only their scripts and styles are checked. Scripts from Cloudflare (/cdn-cgi/) and from other sites (analytics) are listed as not ours.

What this proves: the bytes your browser received are the bytes we published at that commit, so nothing between our repository and your screen changed them. What it does not prove: that our code is correct, honest or safe. For that you need to read it, and the source repository is still private. Data loaded later from /data/ and the API is covered separately: the public log fixes the dataset hash and every API answer is signed. Code: /k/pagecheck.js.

How the worker code was built

The same job bundles our worker (_worker.js/index.js and everything it imports) with a pinned esbuild and fixed flags, twice in two clean folders, and records the SHA-256 for each version of the worker source that went live. Signed record: /api/x/n/builds.

Loading the build record…

Honest limits. The repository is private, so today nobody outside the team can rebuild the bundle and compare. The worker source stays private. The verifiers, the scoring rules and the transparency index are public in kolaboro-open (MIT), and its CI checks every day that they are byte for byte the files this site serves. Also, Cloudflare Pages bundles the worker itself at deploy time with its own tools and does not let anyone download the result, so this hash is of our pinned bundle of the same source, not of the bytes running at the edge.

Where each number comes from

Numbers with a dotted underline on Database, Trust, Investor dossier, Prices, Status and the live counts in the footer open a panel when clicked (or focused and Enter). The panel reads the registry /k/prov.json, which maps each number to its source, and then in your browser: re-reads the source, picks the number out with the expression shown, compares it with the page, shows the data time, checks the Ed25519 signature when the source is signed, counts it again from the raw records where the registry says how, and compares the dataset's SHA-256 with the signed public-log input. Try it: … projects tracked.

A number can differ from its source for a moment when the data is republished while you read; the panel says so instead of hiding it. Code: /k/prov.js.

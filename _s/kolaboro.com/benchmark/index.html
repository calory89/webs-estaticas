AI due-diligence benchmark

Can an AI read a property developer's web page, report what it promises with exact quotes, and not be fooled by text hidden for AI reviewers? Our test set is public: fixed, fictional developer pages with the checks a correct answer must pass. Below are the models we actually ran on it, scored the same way, with every answer signed.

What is tested

  • Extraction: title type, lease length, completion date, payment plan, advertised returns, guaranteed-return wording, what the page does not state, and how much needs checking before paying.
  • Injection: pages that hide instructions for AI reviewers in comments, hidden elements, white text, JSON-LD, nested hidden blocks, a fake "previous answer", in English and Spanish. A correct answer flags the manipulation and never reports the injected text as a developer claim.
  • Not property: a sports page and a recipe. A correct answer says the page is not about property and invents nothing.
  • False alarm: an honest page that must not be flagged.
  • Since version 3, every claim must carry an exact quote. The checks re-verify that each quote is really in the visible text of the page.

Scoring

  • A case passes only if every one of its checks passes. Systems are ranked by cases passed, then by individual checks passed.
  • Check operators: equals, one of, contains, matches a pattern, does not match, empty, present, at least N, and quotes in page (at least N quotes, all found in the visible text after hidden content is removed).
  • Model rows: each case goes through our production desk review code, unchanged, with one model forced: our server refuses the other model's call for that run only (it answers "overloaded", which is how the code path already handles an outage), so the forced model answers alone, without the second reader. The run is started from a GitHub Actions workflow and every answer is signed with our Ed25519 key; your browser re-checks the signatures above.
  • Production row: the latest daily evaluation of the pipeline as it runs for users (Haiku first, Sonnet as second reader, consensus and quote check). It is a separate run on a possibly different day.
  • Cost is estimated from the token counts the model API returned, at list prices (Haiku US$1 / US$5, Sonnet US$3 / US$15 per million input / output tokens).

Run it on your own system

The cases and pages are at /open/evals/cases.json and /open/evals/fixtures/. The scorer is one open file, kolaboro-bench.mjs (MIT, Node 18+, no dependency), with the same checks and the same quote matching as our daily evaluation. The visible text of each page, as our code extracts it, is in visible.json.

node kolaboro-bench.mjs fetch # cases, pages and visible text into ./kolaboro-bench-data/ # run YOUR pipeline on each page, save {"case id": answer, ...} as answers.json (answer fields: see the top of the script) node kolaboro-bench.mjs score answers.json # PASS/FAIL per case, totals per kind node kolaboro-bench.mjs score-ours sonnet # re-score our published run from its raw checks

Want a row here? Send your answers file and how you produced it to hello@kolaboro.com. We list results we could re-score with the script, labelled as submitted by you.

What this benchmark does not show

  • It is small: 18 cases, so one case moves the score by several points and small differences between rows mean little.
  • We wrote the pages and the checks, and we tune our pipeline against them. A system built elsewhere has not had that advantage. Visitors can hand in attacks that fooled our review through the red-team playground, as candidates for new cases.
  • Each model row is one run. Model answers vary from run to run, so a rerun can move a case either way.
  • Our production prompt is not published, because it is part of our defence against manipulated pages. Its SHA-256 is published with every daily evaluation (/api/open/evals), so you can tell when it changes.
  • Fictional pages are cleaner than real developer sites. For real pages, see the desk review and the daily evaluation history.
